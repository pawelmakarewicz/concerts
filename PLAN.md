# Concerts — план

> **Ключевая идея:** залы с отличной акустикой и атмосферой × список моих исполнителей = куда идти.
> Рекомендации концертов вообще — потом.

Следит за афишами залов, куда я хочу попасть ради звука (начиная с **NOSPR, Катовице**),
и сразу пишет в Telegram, когда там появляется концерт в моём вкусе — с объяснением,
**на кого из моих артистов это похоже**. Чтобы успеть на билеты.

Вкус — мои оценки с Radio Paradise.

### Куда растём (не сейчас, но держим в голове)
- **Залы:** цель — все лучшие по звуку филармонии и концертные залы Польши, а не только NOSPR.
  Кандидаты: NOSPR (Катовице), NFM (Вроцлав), Filharmonia Szczecińska, Filharmonia Narodowa (Варшава),
  ICE Kraków, Polska Filharmonia Bałtycka (Гданьск), Filharmonia Łódzka. Список — мой выбор.
- **Как масштабировать залы:** у каждого свой сайт → не писать парсер на каждый, а попробовать
  **ИИ-извлечение афиши** (страница → список событий). Тогда новый зал = строчка в настройках
  (название + адрес афиши). Сначала проверить на NOSPR против обычного парсера (см. шаг 9).
- **Источник вкуса:** сейчас Radio Paradise → потом что-то ещё. TIDAL — не приоритет.

**Правила:**
- Не начинать следующий этап, пока предыдущий не приносит пользу каждую неделю.
- Никаких абстракций заранее. Один зал — один файл с обычными функциями. Общий интерфейс выносить, только когда появится второй зал и станет видно, что у них общего.

## Этап 1. Мои залы

### Как работает
```
Radio Paradise CSV ──► мои артисты с оценками
                                │
NOSPR сайт ──► события ──► новые? ──► ИИ: подходит? на кого похоже? ──► score ≥ 7 ──► Telegram сразу
                 │                                                       иначе ──► пропустить
                 └──► SQLite (что уже видели и оценили)
```

### Решения
1. **Срочно, а не раз в неделю.** На хороший концерт в NOSPR билетов не достать. Проверяем афишу раз в день, подходящее отправляем сразу.
2. **ИИ оценивает каждое новое событие.** Событий в зале мало (десятки в месяц), отсев не нужен.
3. **«Похоже на» — только артисты из моего списка, и это проверяет код.** Если ИИ назвал кого-то не из списка, это имя выкидывается.
4. **ИИ может сказать «не знаю этого артиста».** Это лучше, чем выдуманный жанр.
5. **Факты из афиши, суждения от ИИ.** Дату, программу и ссылку ИИ не придумывает.
6. **Собираем всю опубликованную афишу.** NOSPR публикует сезон целиком, так что новые концерты могут быть и через 8 месяцев. Нас интересует, что событие *новое*, а не что оно скоро.

### Шаги
| # | Шаг | Готово, когда |
|---|---|---|
| 1 | **Каркас**: `uv init`, `.env`, ruff, pytest | `uv run python -m concerts` запускается |
| 2 | **Вкус**: CSV с Radio Paradise → артисты с оценками (оценка артиста = максимум по его песням) | печатается список артистов |
| 3 | **Афиша NOSPR**: разобрать сайт → список событий (дата, название, исполнители, описание, ссылка) | печатаются все концерты из афиши |
| 4 | **ИИ-оценка**: события пачками → score, similar_to, why, confidence | у каждого события есть оценка и «похоже на» |
| 5 | **Проверка качества**: вручную отметить 20 событий «пошёл бы / нет», сравнить с ИИ | понятно, насколько ИИ угадывает (и хватит ли дешёвой модели) |
| 6 | **SQLite**: что уже видели и отправили, кэш оценок ИИ | повторный запуск ничего не дублирует и не тратит деньги на старое |
| 7 | **Telegram**: отправка подходящих новых событий | сообщение приходит в телефон |
| 8 | **Расписание**: запуск раз в день (cron / launchd или GitHub Actions) | всё работает без меня |
| 9 | *(перед вторым залом)* **ИИ-извлечение афиши**: та же страница NOSPR → ИИ → события; сравнить с парсером из шага 3 | понятно, можно ли добавлять залы без своего парсера |

### Данные (минимум)
```python
class Artist(BaseModel):
    name: str
    rating: int                 # 1–10

class Event(BaseModel):
    id: str                     # стабильный: хеш ссылки на событие
    venue: str                  # "NOSPR"
    title: str
    performers: list[str]
    starts_at: datetime
    description: str | None
    url: str

class Verdict(BaseModel):       # ответ ИИ (structured output)
    event_id: str
    score: int                  # 0–10
    similar_to: list[str]       # только из моего списка — проверяется кодом
    why: str                    # 1–2 предложения
    confidence: Literal["high", "medium", "low", "unknown_artist"]
```

### ИИ
- Модель по умолчанию — **`claude-opus-5-5`** ($4 / $20 за 1M токенов вход/выход). Дешёвая альтернатива — **`claude-haiku-5-5`** ($0.10 / $0.50). Какую оставить, решает шаг 5.
- Ответ сразу в Pydantic-модель через `client.messages.parse(..., output_format=...)`.
- Перед чтением ответа проверять `stop_reason` (бывает `"refusal"`).
- Список моих артистов одинаковый в каждом запросе → **prompt caching**.
- События пачками по 10–20, оценки кэшируются в SQLite: одно событие оценивается один раз.
- Для одного зала это центы или единицы долларов в месяц. Проверять по `response.usage`.

```python
class Verdicts(BaseModel):
    verdicts: list[Verdict]

response = client.messages.parse(
    model="claude-opus-5-5",
    max_tokens=16000,
    system=[{"type": "text", "text": taste_prompt, "cache_control": {"type": "ephemeral"}}],
    messages=[{"role": "user", "content": events_text}],
    output_format=Verdicts,
)
if response.stop_reason == "refusal":
    ...  # залогировать и пропустить пачку
verdicts = response.parsed_output.verdicts
```

## Мои артисты рядом — не в этом проекте

## Риски
| Риск | Что делаем |
|---|---|
| NOSPR поменяет сайт | Pydantic-проверка на выходе парсера; если событий 0, это ошибка, а не «ничего нового» |
| ИИ выдумывает жанр неизвестного артиста | Разрешён ответ `unknown_artist`; «похоже на» только из моего списка |
| Пропустили концерт из-за сбоя | Ошибки шлём в тот же Telegram, чтобы было видно, что бот сломался |
